# vesc_servo

Самодостаточная надстройка над CAN-библиотекой
[**motor_vesc**](https://github.com/kakanada/can_vesc_stm32) для STM32, превращающая контроллер
[VESC](https://vesc-project.com/) с редуктором и концевиком в полноценный позиционный привод (серву)
с адекватным поведением у цели - без залипаний, забросов по скорости и раскачки, характерных для
штатного position-PID самой вески.

## Возможности

Штатный контур позиции (Position PID) у VESC на практике у многих проектов ведёт себя нестабильно:
залипает в мёртвой зоне около цели, раскачивается интегратором, может кратковременно превышать
заданную скорость. `vesc_servo` решает это переносом контура позиции на сторону STM32 - веске
отправляется только задание скорости, её собственный, надёжно работающий контур.

- **Работа через редуктор.** Передаточное число (`gear_ratio`), вся система координат и все команды
  - в градусах ВЫХОДНОГО вала, а не вала мотора.
- **Разворачивание угла мотора (unwrap).** Библиотека сама накапливает многооборотный угол по
  телеметрии позиции вески.
- **4 равноправных способа определить нулевую точку** (`homing_mode` в конфиге) - от классического
  хоуминга по концевику до полностью автоматических режимов без единого вызова с вашей стороны, под
  разное железо (концевик, внешний датчик, абсолютный энкодер) - см. "Способ определения нуля" ниже.
- **Зона лимитов** - жёсткая программная защита хода: цель обрезается автоматически, выход
  фактического угла за пределы зоны принудительно и немедленно корректируется.
- **Рабочий диапазон и нормализованное управление** - `VESC_Servo_SetPositionNormalized()` для
  задания цели значением `-1.0..1.0` вместо градусов.
- **Трапецеидальный профиль скорости** с жёсткими пределами максимальной скорости и ускорения
  выходного вала.
- **ПИД-коррекция слежения за профилем**, а не за конечной целью напрямую - вместе с гистерезисом
  убирает залипание и дрожание у цели.
- **Удержание тормозом у цели** (опционально) - защищает ось от смещения вибрацией/внешней
  нагрузкой.
- **Собственная телеметрия сервы** и свой колбэк на приход телеметрии - см. `API_REFERENCE.md`.
- **Самодостаточна**: сама регистрирует веску и подписывается на её телеметрию -
  `VESC_CAN_Init()`/`VESC_CAN_SendXxx()` вручную вызывать не нужно.
- Статический пул хэндлов без malloc, неблокирующий API.

## Требования к настройке в CubeMX

| Что | Настройка |
|---|---|
| CAN/FDCAN периферия | Init в CubeMX, БЕЗ Start - старт делает `can_manager` |
| NVIC | Прерывания приёма/ошибок/опустошения Tx - включить (детали см. `can_manager.h`) |
| `can_manager` | Версия 0.2 или новее (см. [can-managers-stm32](https://github.com/kakanada/can-managers-stm32)) - единолично владеет периферией CAN/FDCAN, инициализируется ДО `vesc_servo` |
| `motor_vesc` | Версия 1.6 или новее (используется `VESC_Config_t.bus`/`CANMGR_Handle_t*`) |
| VESC Tool -> App Settings -> General -> CAN Status Message Rate | Включить статус `STATUS_4`, требуемая частота - см. `API_REFERENCE.md` |
| Кастомный статус №7 вески | Настроить байт состояния концевика (`telemetry.custom_sensor_state`), см. `motor_vesc.h` |
| `stm32_logger` (опционально) | Только если задан `#define LOGGER_ENABLE_VESC_SERVO` - см. "Логирование" ниже |

Периферией CAN/FDCAN единолично владеет `can_manager` - именно его нужно инициализировать
(`CANMGR_Init()`) ДО `VESC_Servo_Init()` и именно его HAL-callback'и подключать (см. пример ниже);
ни `motor_vesc`, ни `vesc_servo` периферию сами не трогают.

## Быстрый старт

Скопируйте `vesc_servo.h` и `vesc_servo.c` в проект рядом с `motor_vesc.h`/`motor_vesc.c` и добавьте
оба `.c`-файла в сборку.

```c
#include "vesc_servo.h"

static CANMGR_Handle_t     *g_can_bus = NULL;
static VESC_Servo_Handle_t *g_servo   = NULL;

/* 0. Шина can_manager - один раз при старте, ДО VESC_Servo_Init() */
void BusSetup(void)
{
    CANMGR_Config_t bus_cfg = {0};
    bus_cfg.hcan = &hcan1;

    g_can_bus = CANMGR_Init(&bus_cfg);
}

/* 1. Один раз при старте программы, ПОСЛЕ BusSetup() выше */
void Setup(void)
{
    VESC_Servo_Config_t servo_cfg = {0};

    servo_cfg.bus        = g_can_bus;
    servo_cfg.vesc_id    = 42;
    servo_cfg.pole_count = 14;

    servo_cfg.gear_ratio                  = 20.0f;
    servo_cfg.max_speed_deg_s             = 60.0f;
    servo_cfg.max_accel_deg_s2            = 120.0f;
    servo_cfg.pid_kp                      = 2.0f;
    servo_cfg.pid_ki                      = 0.5f;
    servo_cfg.pid_kd                      = 0.05f;
    servo_cfg.pid_i_max                   = 20.0f;
    servo_cfg.error_start_correcting_deg  = 10.0f;
    servo_cfg.error_stop_deg              = 5.0f;
    servo_cfg.brake_at_target_fraction    = 0.5f;

    servo_cfg.limit_min_deg   = -100.0f;
    servo_cfg.limit_max_deg   =  100.0f;
    servo_cfg.working_min_deg =  -90.0f;
    servo_cfg.working_max_deg =   90.0f;

    /* Способ определения нуля - см. "Способ определения нуля" ниже. Здесь -
     * классический хоуминг по концевику (значение по умолчанию, можно не
     * указывать явно - оставлено для наглядности): */
    servo_cfg.homing_mode = VESC_SERVO_HOMING_MODE_REQUIRED;

    servo_cfg.limit_switch_pressed_state  = VESC_CUSTOM_SENSOR_PIN_SET;
    servo_cfg.homing_seek_speed_deg_s     = 15.0f;
    servo_cfg.homing_backoff_speed_deg_s  = -10.0f;
    servo_cfg.home_position_deg           = 0.0f;

    g_servo = VESC_Servo_Init(&servo_cfg);
    VESC_Servo_SetBrakeAtTarget(g_servo, 1U);
}

/* 2. Когда решите, что пора - не обязательно сразу при старте. Нужен только при
 * homing_mode == REQUIRED/MANUAL_EXTERNAL - для ZERO_AT_BOOT/TRUST_ABSOLUTE серва
 * готова сама, без единого вызова - см. "Способ определения нуля" ниже. */
void OnHomingRequested(void)
{
    VESC_Servo_StartHoming(g_servo);
}

/* 3. Где угодно в коде, по мере расчёта нового целевого угла */
void OnNewTargetComputed(float target_deg)
{
    if (VESC_Servo_GetState(g_servo) == VESC_SERVO_STATE_READY)
    {
        VESC_Servo_SetPosition(g_servo, target_deg);
        /* либо, если удобнее в диапазоне -1..1 относительно рабочего диапазона: */
        /* VESC_Servo_SetPositionNormalized(g_servo, joystick_value); */
    }
}

/* 4. (Опционально) изредка, например раз в секунду - см. "Диагностика потери связи" */
void HousekeepingTick(void)
{
    VESC_Servo_CheckAlive(g_servo);
}

/* Обязательные HAL-callback'и CAN - теперь это дело can_manager, не
 * motor_vesc/vesc_servo (бэкенд bxCAN, например STM32F4) */
void HAL_CAN_RxFifo0MsgPendingCallback(CAN_HandleTypeDef *hcan)
{
    CANMGR_RxFifo_Handler(hcan);
}
void HAL_CAN_TxMailbox0CompleteCallback(CAN_HandleTypeDef *hcan) { CANMGR_TxComplete_Handler(hcan); }
void HAL_CAN_TxMailbox1CompleteCallback(CAN_HandleTypeDef *hcan) { CANMGR_TxComplete_Handler(hcan); }
void HAL_CAN_TxMailbox2CompleteCallback(CAN_HandleTypeDef *hcan) { CANMGR_TxComplete_Handler(hcan); }
/* Без него шина не восстановится сама после Bus-Off - см. can_manager.h */
void HAL_CAN_ErrorCallback(CAN_HandleTypeDef *hcan) { CANMGR_ErrorStatus_Handler(hcan); }
```

Бэкенд FDCAN (STM32H7 и т.п.) использует `HAL_FDCAN_RxFifo0Callback`/
`HAL_FDCAN_TxFifoEmptyCallback`/`HAL_FDCAN_ErrorStatusCallback` вместо bxCAN-колбэков выше - см.
`can_manager.h`.

Более подробный, аннотированный пример (в т.ч. свой колбэк телеметрии и нормализованное управление)
- см. [`vesc_servo_example.c`](./vesc_servo_example.c). Полный список функций и структур - в
[`API_REFERENCE.md`](./API_REFERENCE.md).

## Событийная модель

`VESC_Servo_Init()` сама подписывается на телеметрию вески, и весь контур (разворачивание угла,
хоуминг, профиль, ПИД) продвигается сам по мере прихода телеметрии по CAN - вызывать какую-либо
функцию-тик в цикле или из таймера не нужно.

Обратная сторона: контур не может сам заметить **полную** тишину на шине (обработчик просто
перестаёт вызываться) - см. [Диагностика потери связи](#диагностика-потери-связи) ниже.

## Зона лимитов и рабочий диапазон

Две независимые пары границ, обе - в градусах ВЫХОДНОГО вала:

### Зона лимитов (`limit_min_deg` / `limit_max_deg`)

Жёсткая защита хода. Ни `VESC_Servo_SetPosition()`, ни `VESC_Servo_SetPositionNormalized()` не могут
задать цель за пределами этой зоны - значение обрезается автоматически. Если фактический угол всё же
оказался снаружи (внешнее воздействие, ошибка в другом месте прошивки и т.п.) - контур принудительно
едет обратно внутрь, **игнорируя гистерезис** (`error_start_correcting_deg`/`error_stop_deg`):
коррекция запускается немедленно и не останавливается, пока угол не вернётся в зону, даже если
формальная ошибка меньше обычного порога запуска.

### Рабочий диапазон (`working_min_deg` / `working_max_deg`)

**Это НЕ лимит**, а только шкала для `VESC_Servo_SetPositionNormalized()`:

- `normalized == -1.0` → `working_min_deg`
- `normalized == 0.0` → середина между `working_min_deg` и `working_max_deg`
- `normalized == 1.0` → `working_max_deg`

Значения вне `-1.0..1.0` (например `-1.2`) линейно **экстраполируются** за рабочий диапазон, но
итоговый угол всё равно обрезается по **зоне лимитов**, а не по рабочему диапазону - рабочий
диапазон обязан целиком помещаться внутри зоны лимитов.

```
limit_min_deg          working_min_deg      working_max_deg          limit_max_deg
     |-----------------------|====================|------------------------|
     ←   -1.2 экстраполирует   -1.0             1.0    1.2 экстраполирует  →
         сюда, но обрежется                                сюда, но обрежется
         по limit_min_deg                                  по limit_max_deg
```

```c
servo_cfg.limit_min_deg   = -100.0f;
servo_cfg.limit_max_deg   =  100.0f;
servo_cfg.working_min_deg =  -90.0f;
servo_cfg.working_max_deg =   90.0f;

VESC_Servo_SetPositionNormalized(g_servo, 0.0f);   /* -> 0°    (середина рабочего диапазона) */
VESC_Servo_SetPositionNormalized(g_servo, 1.0f);   /* -> 90°   (working_max_deg)             */
VESC_Servo_SetPositionNormalized(g_servo, 1.2f);   /* -> 100°  (экстраполяция, но обрезано по limit_max_deg) */
VESC_Servo_SetPositionNormalized(g_servo, 2.0f);   /* -> 100°  (экстраполяция ушла бы на 180°, но обрезано)  */
```

## Свой колбэк телеметрии сервы

Раз слот колбэка телеметрии самой вески занят сервой изнутри, для внешнего кода, которому тоже нужно
реагировать на приход телеметрии (например, чтобы сразу переслать что-то в общий пакет телеметрии
системы), предусмотрен отдельный, аналогичный по духу колбэк **одним уровнем выше** -
`VESC_Servo_SetTelemetryCallback()`. Он вызывается на каждый принятый статусный пакет вески (все 7
видов, не только `STATUS_4`), но в обработчик приходит указатель на серву, а не на веску - внутри
сразу доступны и `s->vesc->telemetry` (сырая телеметрия вески), и `s->telemetry` (готовая телеметрия
сервы), уже свежие на момент вызова.

```c
void OnTelemetry(VESC_Servo_Handle_t *s, VESC_CAN_PacketId_t status_id)
{
    /* удобно скопировать что нужно одним махом, не дожидаясь опроса */
    g_system_telemetry.wheel_angle_deg = s->telemetry.position_deg;
    g_system_telemetry.wheel_current_a = s->vesc->telemetry.current;
}

VESC_Servo_SetTelemetryCallback(g_servo, OnTelemetry);
```

> Как и колбэк `motor_vesc`, этот колбэк вызывается **из прерывания** приёма CAN - должен быть
> быстрым и не блокирующим (никаких `HAL_Delay()`, долгих вычислений или ожиданий внутри).

## Жизненный цикл состояния

```
VESC_Servo_Init()
        |
        v
   DISABLED  --StartHoming()-->  HOMING  --концевик найден-->  READY
        |                            |                            ^
        |     SetCurrentPosition()   |                            |
        +--- (либо АВТОМАТИЧЕСКИ,----+----------------------------+
        |     см. homing_mode) ------+
        ^                            |                            |
        |                        таймаут                          |
        |                     CheckAlive()/разрыв STATUS_4         |
        |                            v                             |
        +<---------------------- FAULT <----- CheckAlive() /--------+
        ^                            |         разрыв STATUS_4
        |     SetCurrentPosition() / StartHoming() / Enable()*
        +----------------------------+
```
\* `Enable()` выводит из `FAULT` только если серва прошла хоуминг ранее (`VESC_Servo_IsHomed()`) И
телеметрия к моменту вызова уже снова свежая - т.е. только для `FAULT`, вызванного
`CheckAlive()`/разрывом `STATUS_4` (потеря связи), а не для `FAULT` от провалившегося хоуминга (там
`IsHomed() == 0`, `Enable()` откажет).

- `DISABLED` - контур выключен, команды не шлются. При `homing_mode` `ZERO_AT_BOOT`/`TRUST_ABSOLUTE`
  это состояние длится только до первой телеметрии от вески (обычно доли секунды) - дальше см. ниже.
- `HOMING` - идёт поиск нуля (`VESC_Servo_GetHomingState()` для этапа). Прерывается явным
  `Disable()` (засчитывается как неудача) либо переходом в `FAULT`.
- `READY` - позиция достоверна, доступен `VESC_Servo_SetPosition()`.
- `FAULT` - хоуминг провалился по таймауту; либо `VESC_Servo_CheckAlive()` обнаружила полную потерю
  связи с веской; либо разрыв между приходами `STATUS_4` превысил `max_step_dt_ms` - накопленная до
  разрыва позиция более не достоверна.

`VESC_Servo_StartHoming()` и `VESC_Servo_SetCurrentPosition()` останавливают мотор перед сменой
состояния, если прерывают что-то активное (едущую коррекцию или другой хоуминг) - предыдущая команда
скорости не продолжает исполняться до следующего тика.

## Способ определения нуля

Помимо классического хоуминга по концевику, `vesc_servo` умеет определять точку отсчёта угла ещё
тремя способами - все 4 варианта выбираются ОДНИМ полем конфига, `homing_mode`
(`VESC_Servo_HomingMode_t`), под конкретное железо:

| `homing_mode` | Что происходит | Когда использовать |
|---|---|---|
| `VESC_SERVO_HOMING_MODE_REQUIRED` (по умолчанию) | Ничего автоматически - `DISABLED`, пока вы сами не вызовете `VESC_Servo_StartHoming()` (поиск нуля по концевику). | Есть концевик, нужна физическая повторяемость нуля между включениями. |
| `VESC_SERVO_HOMING_MODE_ZERO_AT_BOOT` | Автоматически: на первой телеметрии текущий угол объявляется `home_position_deg` - "где вал стоял при включении, там и ноль". Сразу `READY`. | Концевика нет, абсолютная повторяемость нуля между включениями не важна (либо механика гарантированно не двигается без питания). |
| `VESC_SERVO_HOMING_MODE_MANUAL_EXTERNAL` | Как `REQUIRED` (ничего автоматически), но вместо `StartHoming()` вы сами вызываете `VESC_Servo_SetCurrentPosition()` со значением от своего внешнего источника (другой датчик, сохранённое во внепамять значение). | Ноль известен из источника, не связанного с концевиком/телеметрией вески. |
| `VESC_SERVO_HOMING_MODE_TRUST_ABSOLUTE` | Автоматически: угол, который веска ОТДАЁТ на первой телеметрии, принимается КАК ЕСТЬ, без какой-либо коррекции (`home_position_deg` не участвует). Сразу `READY`. | На моторе абсолютный энкодер, чей "0" уже физически откалиброван при сборке - веска фактически "уже отхоумлена" сама, ещё до старта STM32. |

Независимо от выбранного режима, `VESC_Servo_StartHoming()`/`SetCurrentPosition()` остаются доступны
для ручного вызова в любой момент (например перехоуминг по концевику вручную поверх обычно
автоматического режима).

⚠️ **`ZERO_AT_BOOT`**: ноль здесь **не физически воспроизводим** между включениями - если вал
сместился, пока было выключено питание (внешняя сила, вибрация, ручной поворот), следующее включение
примет НОВОЕ положение за ноль, без проверки. Единственный физически воспроизводимый способ -
`REQUIRED` (концевик).

⚠️ **`TRUST_ABSOLUTE`**: сырой угол вески - это угол МОТОРА, однооборотный (0..360°). При
`gear_ratio > 1` (обычный редуктор) он даёт однозначный угол выходного вала только в пределах первого
оборота мотора от истинного нуля - если на старте выходной вал уже дальше (а с редуктором это
нормальный рабочий случай), результат будет ошибочным на целое число оборотов мотора. Без
неоднозначности - только при `gear_ratio == 1` (прямой привод) либо когда абсолютный энкодер стоит на
самом выходном валу (тогда см. `MANUAL_EXTERNAL` со значением от него). Подробности - см.
`vesc_servo.h`.

## Диагностика потери связи

Контур продвигается обработчиком телеметрии, который вызывается только когда пакет **действительно
пришёл** - если связь с веской пропадёт полностью (обрыв шины, зависание вески и т.п.), обработчик
просто перестанет вызываться, и заметить это изнутри самого себя модуль не может.

Подстраховка - три вещи:

1. **Штатный таймаут потери команд самой вески** (настраивается в VESC Tool) - если веска перестаёт
   получать команды дольше этого таймаута, она сама останавливает мотор независимо от STM32.
   Работает всегда, без участия `vesc_servo`.
2. **`VESC_Servo_CheckAlive()`** - необязательная функция для тех, кому важно, чтобы
   `VESC_Servo_GetState()` корректно показывал `VESC_SERVO_STATE_FAULT` при полной тишине на шине
   (например для индикации на UI). Вызывайте её изредка (раз в секунду и реже вполне достаточно) из
   любого своего периодического места.
3. **Автоматический переход в `FAULT` при разрыве `STATUS_4` длиннее `max_step_dt_ms`** - в отличие
   от пп. 1-2 (полная тишина), это модуль обнаруживает САМ: если очередной `STATUS_4` всё же пришёл,
   но с опозданием больше `max_step_dt_ms`, вал мог провернуться неотслеживаемо много - серва сама
   останавливает мотор и переходит в `FAULT`, не дожидаясь `CheckAlive()`.

## Логирование (опционально)

Модуль умеет логировать ключевые события (ошибки `Init`, вход в `FAULT`, начало/конец хоуминга)
через библиотеку [`stm32_logger`](../../stm32_logger/index.md), но не требует её - зависимость
целиком опциональная и включается одним `#define` до подключения `vesc_servo.c` к сборке:

```c
#define LOGGER_ENABLE_VESC_SERVO
```

Без этого `define` модуль собирается и работает как прежде, не подключая ни одного файла
`stm32_logger`. С ним - `logger_codes.h` вашего проекта должен резервировать коды
`LOG_CODE_VESC_SERVO_*` под тем же `define` (правила такого резервирования - в шапке
`logger_codes.h` самой `stm32_logger`). Полный список кодов - в `vesc_servo.h` (раздел
"ОПЦИОНАЛЬНАЯ ИНТЕГРАЦИЯ С stm32_logger").

## Особенности железа

- **Энкодер вески меряет вал МОТОРА, до редуктора**, и оборачивается каждый оборот мотора
  (`telemetry.pid_pos` - НЕ многооборотное значение) - выходной вал при этом крутится в
  `gear_ratio` раз медленнее; накопленный угол мотора (`motor_unwrapped_deg`) хранится как `float`
  и на практике для типичной сервы с ограниченным ходом точности хватает с большим запасом, но при
  очень долгой непрерывной работе с вращением в одну сторону (миллионы оборотов мотора без
  перезапуска МК) погрешность накопления суммы может стать заметной.
- **Концевик нуля висит на самой веске**, а не на STM32, и приходит по CAN в её кастомном статусе
  №7 (`VESC_CAN_PACKET_STATUS_7` / `telemetry.custom_sensor_state`, см. `motor_vesc.h`).

## Важные предостережения

- **Частота `STATUS_4` в VESC Tool критична.** Между двумя приходами `STATUS_4` вал мотора не должен
  успевать провернуться больше, чем на пол-оборота - см. требуемую частоту в
  `API_REFERENCE.md`/`vesc_servo.h`.
- **Один слот под колбэк телеметрии на веску.** `VESC_Servo_Init()` занимает
  `VESC_CAN_SetTelemetryCallback()` этой вески под себя. Если вашему коду тоже нужно реагировать на
  приход телеметрии этой же вески - используйте `VESC_Servo_SetTelemetryCallback()` (см. выше), а не
  `VESC_CAN_SetTelemetryCallback()` напрямую (это его отключит).
- **Не вызывайте API `motor_vesc` напрямую** для вески, обёрнутой сервой - `VESC_CAN_SendXxx()`
  будет соревноваться с командами контура позиции. Читать `h->telemetry` напрямую (через
  `s->vesc->telemetry`) - можно, это безопасно.
- **Не совмещайте с "памятью положения" нижнего уровня** (`VESC_CAN_SetPositionMemoryEnabled` в
  `motor_vesc`) для той же вески - пересчёт офсета там может создать ложный скачок угла, который
  `vesc_servo` примет за реальное вращение вала.
- **Зона лимитов - это программная защита**, реагирующая не быстрее частоты `STATUS_4` - не жёсткая
  аппаратная защита с нулевой задержкой, не заменяет физический концевик/механический упор там, где
  цена ошибки высока.
- **Minimum ERPM самой вески может молча съедать мелкие корректирующие команды на геаред-приводах.**
  ПИД слежения около цели шлёт всё более мелкие команды скорости по мере схождения к цели - в
  электрических RPM мотора (через `gear_ratio`) они легко проваливаются ниже `Motor Settings -> PID
  Controllers -> Speed -> Minimum ERPM` в VESC Tool (по умолчанию ~900), и веска их просто
  игнорирует.

## Честные ограничения

- Поддерживается только управление по скорости (штатный контур скорости VESC) - режим управления по
  току не реализован.
- Нет функции прямого задания скорости в обход контура позиции (джог-режим) - только
  позиционирование через `VESC_Servo_SetPosition()`/`SetPositionNormalized()`.
- Отправляемая веске команда скорости не сглаживается программным фильтром - при агрессивных
  настройках ускорения на стороне VESC (см. предупреждение про Minimum ERPM выше) это может
  ощущаться как резкое поведение привода.
- Поддерживаются только вращающиеся приводы - линейные приводы (например шкив с ремнём) не
  поддерживаются, передаточное число трактуется как обычный вращательный редуктор.
- Полный набор команд конфигурации VESC (`COMM_SET_MCCONF_TEMP` и аналогичные) не отправляется -
  используются только простые однокадровые команды протокола VESC через `motor_vesc`.
